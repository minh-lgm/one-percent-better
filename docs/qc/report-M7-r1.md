## 4. Defect

### M7-D1 — Một id hợp lệ ở máy nhưng cloud từ chối làm đồng bộ kẹt vĩnh viễn  [Major]
- Bước tái hiện: sửa một bản sao `e2e/fixtures/sample-backup.json`: đổi `id` của goal đầu tiên và `goalId` các entry của nó thành chuỗi 70 ký tự `xxxx…`. Cloud mock đang chạy (`npm run mock:supabase`, `npm run build:cloud-e2e && npm run preview:cloud-e2e`). Settings → Import backup → chọn file → Replace all data (chưa đăng nhập; importer chấp nhận). Settings → Sign in with Google → Minh Test. Chờ 8 giây, mở lại Settings. (Tự động: `tests/qc/cloud/m7-r1-probe.spec.ts` "poison pill"; Vitest `tests/qc/m7-r1-contract.test.ts` hai `it.fails`.)
- Mong đợi: hoặc importer từ chối file có id dài hơn mức cloud chấp nhận (cùng một giới hạn ở hai biên), hoặc 4 goal còn lại và các entry của chúng vẫn lên tài khoản (NFR-05, FR-45; SQL ghi rõ `id` 1–64 ký tự, "local id (UUID or id from an old backup file)").
- Thực tế: chip `Couldn't sync` + `Retry`, card ghi "Couldn't reach your account just now…" (lời giải thích sai), `Waiting to sync 29 changes`, mock có 0 goal / 0 entry sống. `POST /rest/v1/goals` (5 hàng) bị từ chối nguyên lô (check constraint → 400) nên không hàng nào lên; thử lại mãi theo backoff, không có cách nào trong UI để thoát (chỉ Remove data hoặc import lại file khác). Cùng nguyên nhân với `goalId` và id entry dài hơn 64. ## 9. Đề xuất (không chặn)

1. Ngoài D1: nếu một lô push bị server từ chối vì ràng buộc dữ liệu (4xx không phải 401/403/429) thì nên tách lô để cô lập hàng hỏng và báo lỗi đúng; `SYNC_UNREACHABLE` hiện nói "Couldn't reach your account", sai nguyên nhân.
2. `playwright.config.ts` không giới hạn số worker (24 lõi → 12 worker); Vitest đã có `maxWorkers: 8` vì cùng lý do (M5-D2). Với bộ 484 test, 12 worker làm các test nặng (axe mọi màn, large dataset, import 16k entry) chạm timeout 60 s/10 s; `--workers=8` xanh 2/2. Đề nghị dev đặt trần worker hoặc nới timeout các test nặng (`e2e/m5-journey` M5-AC8 mất 35 s khi bộ test nhỏ hơn).
3. Tombstone không bao giờ bị dọn: khi cloud tắt (hoặc chưa đăng nhập) mọi goal/entry đã xoá và mọi dòng bị Import thay thế ở lại IndexedDB mãi (ẩn khỏi UI/export, nhưng chiếm chỗ và vẫn là dữ liệu đã xoá trên đĩa). Cân nhắc dọn tombstone khi cloud tắt hoặc đã đồng bộ (dirty 0) quá N ngày.
4. Gộp hai thiết bị có thể vượt ràng buộc mà từng thiết bị tự giữ (hai máy offline mỗi máy ghi 1.000 phút cho cùng goal/ngày → 2.000 phút; sửa chu kỳ goal ở A trong khi B ghi entry ngoài khoảng mới). Đã kiểm: app vẫn dùng bình thường, không lỗi, không crash (`m7-r1-edge.spec.ts`), chỉ là dữ liệu vượt giới hạn nhập tay. Nên ghi nhận ở planner (A-24).
5. Brand: logo 28 px trong sidebar không đọc được chữ "BETTER"; chữ hiển thị nay chỉ là "Better per Day" (mất "1%"), tên truy cập vẫn đủ. Cân nhắc mark lớn hơn hoặc chữ "1%" riêng; designer cần cập nhật DESIGN §5 (deviation đã được orchestrator chấp nhận).
6. Bench `fake-indexeddb` 132–136 ms (dev 70,7; M6 57,1) cho Review 5 goal: vẫn < 200 ms và chỉ là số thông tin, nhưng gấp đôi M6; lọc tombstone toàn bảng (`isLive` trên `toArray`) đáng nhìn lại nếu dữ liệu lớn hơn. Import 16k entry: 3,1 s khi chạy riêng, 8–12 s dưới tải.
